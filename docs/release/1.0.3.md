# 1.0.3

> 发布日期：2026-11-04
> versionCode：14
> 更新方式：**自由更新**（`forceUpdate: false`）

一句话：任务包不再卡在 20MB，启动也不会再去拉一个没装的游戏，顺带修了两轮卡顿。

---

## 修复 · 任务包上限 20MB → 500MB

超过 20MB 的包在导入时会直接失败。原来的理由是「模板图几百 KB 就够」，但带整段录屏、
十几个界面的高清模板、或内嵌识别资源的包很容易超。

**光把数字改大不行。** 原来的解压是这样的：

```kotlin
val bytes: ByteArray = 整个 zip     // 一份
val assets: Map<String, ByteArray>  // 每个 entry 再来一份
```

峰值 ≈ 包体积 × 2。20MB 时看不出来，500MB 会直接 OOM —— 而 OOM 是系统杀进程，
用户看到的是「点了安装，App 没了」，连个错误提示都没有。

现在改成边解压边写临时目录：

```
zip 流 → 逐 entry 读到 64KB buffer → 直接写 .tmp-xxx/xxx
                                    → 校验（需要的是文件名集合，不是内容）
                                    → rename 成正式目录
```

内存里只留 `task.json`（几百 KB）。「校验通过才落盘」的保证没变：校验在**改名前**做，
失败的包只会留下临时目录，`finally` 里清掉。

单个文件上限同时从 6MB 提到 64MB。

## 修复 · 启动游戏去拉了一个没装的包

「启动游戏」节点里的客户端选择会被重置回默认官服（画面校准、任务链自愈、误点都可能）。
而机器上装的可能是云游戏 —— 于是启动超时后它会认认真真去拉 `com.miHoYo.hkrpg`：

```
拉不起来 → 重试 → 再失败 → 报"启动超时"
```

日志里只显示普通的超时，完全看不出是包名错了。用户以为是网络或游戏问题。

引擎里其实有两个包名：

| 来源 | 用途 | 可信度 |
|---|---|---|
| `params.packageName`（任务参数） | StartUp 任务自己带 | 会被重置 |
| `pkg`（`setPackage` 传入） | force-stop、画面漂移检测、本次会话目标 | 来自用户实际选的客户端 |

原来只信前者。现在交叉校验：

```kotlin
if (declaredPkg != pkg && !isInstalled(declaredPkg) && isInstalled(pkg)) {
    用 pkg，并记一条警告
}
```

## 调整 · 画面异常自愈 50s → 60s

等「点击进入」50 秒还没出现，就判定画面被放大裁切（荣耀类 ROM 的双重缩放 bug），
强制把 task 移到主屏再移回来，逼 WindowManager 重算。

云游戏建流 + 首次加载本来就慢，50 秒偶尔把「真的在加载」误判成「画面坏了」，
白踢一次重排。放宽到 60 秒；总上限 180 秒，留 120 秒给重排后重新加载。

## 调整 · 导入提示可以不再弹

免责声明底部加了一个勾选框。勾了之后导入直接开文件选择器。

弹窗本身没删，设置页「导入任务包」那条的描述里仍然写着来源和风险；
只是一个连导入十个包的人不该被拦十次。

## 优化 · 卡顿（两轮）

**任务执行路径**（6 处）——问题不是死循环，是同一帧被识别了好几遍：

| 位置 | 原来的浪费 |
|---|---|
| `gotoGuideTab` | 连着调两次 `guideTab()`，对同一帧跑两遍全屏 OCR（0.5~1.5s × 2） |
| `switchGuideTab` 逐格试探 | 每格点两次 + 两次 OCR |
| `claimMilestones` | 先自己判一次弹窗，再调 `dismissRewardPopup`（内部又判一次），5 个里程碑多跑 5 次 |
| `claimAll` | `?: return@repeat` 是 continue 不是 break，找不到「领取」也白跑 8 轮，每轮再截 5 次帧 |
| 等大厅 / 等指南页 | 轮询 120ms / 300ms，而单轮成本（取帧 + 整帧归一化）已经贴近间隔本身 |
| 日志落盘 | 75ms 一次 → 每秒 13 次磁盘 flush + 13 次 UI 列表替换 |

**UI 层**（4 处）——都是「整页跟着重组」级别：

| 位置 | 问题 |
|---|---|
| `BackgroundTaskView` | 在根节点 collect `markers`，而它按触摸事件频率更新（拖画面时最高 120Hz）—— 恰恰是最需要帧率的时候整页重组 |
| 屏保 | 订阅整个 750 条日志，只用最后一条；日志每 250ms 刷一次 = 每秒重组 4 次 |
| 设置页 | `Toast.makeText` + `clearSettingsMessage()` 写在组合体里，绘制期间回写状态 |
| 日志面板 | 组合期直接读 `listState.canScrollForward`，滚动中一翻转就整树判脏 |

**已知未修**：每帧 8MB 的 Bitmap 不 recycle。截图接口在 binder 线程读同一个 `screenshot`
引用，任务线程回收会踩 `recycled bitmap` —— 真要治得改成引用计数或双缓冲，不是调参能解决的。
